# OOXX 两端对齐文档

> 目的：让鸿蒙端和安卓端在 UI 语义、业务规则、数据结构和后续跨端通信上保持一致。两端可以使用不同控件和布局实现，但不能出现规则和字段含义不一致。

## 1. 当前版本范围

- 第一版：6×6、固定题库、竖屏、单机。
- 页面：首页、游戏页、规则页。
- 支持：填入 X/O、检查、错误高亮、完成提示、计时、重启。
- 暂不实现：登录注册、联网、标记、撤销/重做、题目生成器。

## 2. UI 对齐

| 项目 | 统一要求 |
| --- | --- |
| 视觉方向 | 保留康思 OOXX 的紫色和逻辑游戏感，重新适配移动端 |
| 屏幕 | 第一版只做竖屏 |
| 首页 | 标题、开始游戏、游戏规则入口 |
| 游戏页 | 返回、题目/计时信息、6×6 棋盘、检查、重启 |
| 规则页 | 三条规则、点击循环说明 |
| 棋盘 | 6×6 正方形；固定格和可编辑格视觉区分 |
| 格子点击 | 空白 → X → O → 空白；固定格不可点击 |
| 检查结果 | 只在点击“检查”后显示错误，不实时提示 |
| 完成状态 | 显示成功提示和完成用时，禁止继续修改或明确提供重新开始入口 |

颜色、字号、圆角、间距、按钮高度以 Figma 设计稿为准。鸿蒙和安卓不要求像素完全相同，但页面层级、信息顺序、交互结果必须一致。

## 3. 业务对齐

### 3.1 统一枚举

```text
CellValue: EMPTY、X、O
GameStatus: READY、PLAYING、COMPLETED
RoomMode: SINGLE、COLLABORATIVE、COMPETITIVE
```

固定题目格不要写入玩家可编辑状态，建议使用：

```text
clueBoard：固定格布局
playerBoard：玩家填写内容
```

### 3.2 统一规则

1. 每行、每列不能出现三个及以上连续相同符号。
2. 每行、每列 X 和 O 数量相同。
3. 行不能重复，列不能重复。
4. 只有填满且全部满足规则，才算完成。
5. 固定格不能修改。
6. 检查时返回错误格或错误行列；客户端负责展示高亮。

### 3.3 统一操作

```text
startPuzzle(puzzleId)
setCell(row, col, value)
checkPuzzle()
restartPuzzle()
```

单机版由本地仓库执行；联网版由远程仓库发送操作请求。页面不直接调用规则服务、存储或 WebSocket。

## 4. 状态流转

```text
READY → PLAYING → COMPLETED
              ↘ 检查失败后继续 PLAYING
```

- 点击格子：更新玩家棋盘和界面。
- 点击检查：计算错误位置；有错误则继续游戏，无错误且已填满则完成。
- 点击重启：恢复题目固定格，清空玩家填写，计时重新开始。
- 联网后：客户端只提交操作意图，服务器返回的状态覆盖本地状态。

## 5. 跨端通信对齐

统一使用 JSON，字段使用 `camelCase`：

```json
{
  "type": "cellUpdate",
  "requestId": "请求编号",
  "roomId": "房间编号",
  "playerId": "玩家编号",
  "version": 3,
  "payload": {}
}
```

第一批消息：

```text
createRoom、joinRoom、roomState、cellUpdate、checkResult、restartPuzzle、puzzleCompleted、error、ping、pong
```

跨端必须遵守：

- 服务端按接收顺序处理操作。
- 服务端维护最终棋盘和 `version`。
- 客户端不能自行宣布最终完成结果。
- 操作被接受后，服务端广播确认状态。
- 版本过旧时返回最新 `roomState`，客户端覆盖本地状态。
- 错误码统一使用：`ROOM_NOT_FOUND`、`INVALID_CELL`、`CELL_LOCKED`、`INVALID_VALUE`、`VERSION_CONFLICT` 等。

详细协议见 [`WEBSOCKET_PROTOCOL.md`](./WEBSOCKET_PROTOCOL.md)。

## 6. 两端分工边界

### 鸿蒙端

- ArkTS + ArkUI。
- 先实现单机本地仓库。
- 提前保留 `GameRepository` 接口，后续替换为远程仓库。

### 安卓端

- Kotlin + XML。
- 按本文件实现同样的页面流程、模型和校验规则。
- 不直接复制鸿蒙代码，只对齐业务契约和协议字段。

### 服务端

- 后续再确认 Node.js + 原生 WebSocket。
- 负责房间、操作顺序、权威状态、版本号和完成结果。

## 7. Figma 是否要先做

**建议先做一个精简设计稿，再开始页面代码。** 不需要一开始画完整高保真网站，只画第一版必须的内容：

1. 首页、游戏页、规则页。
2. 游戏页的默认、检查错误、完成三种状态。
3. 棋盘格、固定格、X、O、错误格、按钮等基础组件。
4. 颜色、字号、间距、圆角和按钮尺寸。

Figma 的作用是统一两端视觉和交互，不是限制两端必须使用相同控件。先完成这份最小设计稿，安卓端和鸿蒙端再同时开工，返工最少。
