# OOXX 服务端答辩说明（零后端基础版）

## 1. 一句话说明

服务端是网络对局的**唯一裁判**：客户端只提交“我想在这里落子”，服务端负责检查是否合法、修改棋盘、判断胜负，并把同一份结果广播给所有客户端。

## 2. 为什么需要服务端

如果 Android 和鸿蒙端各自判断结果，可能出现：

- 两端棋盘不一致；
- 双方同时落子；
- 客户端篡改回合或胜负；
- 断线后房间状态混乱。

因此本项目采用“服务端权威”设计。客户端负责显示和操作，最终状态以服务端为准。

## 3. 技术选型

| 项目 | 方案 | 用途 |
|---|---|---|
| 运行环境 | Node.js | 执行服务端 JavaScript |
| HTTP | Node.js 原生 `http` | 健康检查、每日题目、排行榜 |
| 实时通信 | 标准 WebSocket + `ws` | 房间、落子、认输、状态广播 |
| 房间存储 | 内存 `Map` | 保存当前在线房间和连接 |
| 排行榜存储 | JSON 文件 | 保存积分、胜负和平局次数 |
| 测试 | Node.js 原生测试框架 | 测试规则、协议和房间状态机 |

没有使用 Socket.IO、Web 框架或数据库，结构小，便于课程项目展示。

## 4. 组成部分

```text
server/
├─ src/index.js            服务入口：HTTP、WebSocket、消息分发
├─ src/room-service.js     房间状态机：创建、加入、落子、认输、离开
├─ src/game-rules.js       棋盘、胜负、平局和房间快照
├─ src/ranking-store.js    积分计算与 JSON 持久化
├─ src/puzzles.js          每日残局数据
├─ data/rankings.json      排行榜数据
├─ test/                   自动化测试
└─ deploy.sh               Ubuntu 服务器部署脚本
```

可以把它理解为：

- `index.js` 是**前台接待**；
- `room-service.js` 是**裁判**；
- `game-rules.js` 是**比赛规则**；
- `ranking-store.js` 是**记分员**。

## 5. 一次网络对局怎么实现

1. 两个客户端连接 `ws://服务器:9527/ws`。
2. 客户端发送 `hello`，声明玩家 ID 和昵称。
3. 玩家 A 创建房间，服务端生成 6 位房间码，并分配棋子 `X`。
4. 玩家 B 输入房间码加入，被分配棋子 `O`，房间开始。
5. 客户端发送落子坐标；服务端依次检查身份、回合、坐标和格子占用。
6. 合法落子写入服务端棋盘，再判断胜利或平局。
7. 服务端向房间内所有连接广播完整 `room.state`。
8. 对局结束后，服务端结算积分并写入排行榜文件。

核心原则：**先验证，后修改，再广播**。

## 6. WebSocket 实现机理

WebSocket 是建立在 TCP 上的长连接。与普通 HTTP“一问一答”不同，连接建立后：

- 客户端可以随时发消息；
- 服务端也可以主动广播；
- 不必每次落子都重新建立连接。

本项目所有消息都使用 JSON，并通过 `type` 区分用途。主要消息如下：

| 方向 | `type` | 作用 |
|---|---|---|
| 客户端 → 服务端 | `hello` | 登记玩家信息 |
| 客户端 → 服务端 | `room.create` | 创建房间 |
| 客户端 → 服务端 | `room.join` | 加入或观战 |
| 客户端 → 服务端 | `move` | 提交落子坐标 |
| 客户端 → 服务端 | `game.surrender` | 认输 |
| 服务端 → 客户端 | `room.state` | 广播权威房间状态 |
| 服务端 → 客户端 | `error` | 返回业务错误码 |

Android、鸿蒙和 Server 共同读取同一套规则与协议契约，避免三端对字段或规则理解不一致。

## 7. 房间状态机

房间只有三个状态：

```text
WAITING ──第二名玩家加入──> PLAYING ──胜利/平局/认输──> FINISHED
   ^                            |
   └──────对局玩家离开──────────┘
```

| 状态 | 含义 | 允许的主要操作 |
|---|---|---|
| `WAITING` | 等待第二名玩家 | 加入、观战、离开 |
| `PLAYING` | 正在对局 | 落子、认输、离开 |
| `FINISHED` | 已产生最终结果 | 查看、观战、离开 |

特殊处理：

- 观战者离开，不影响正在进行的对局；
- 对局玩家中途离开，棋盘清空，剩余玩家变为 `X`，房间回到 `WAITING`；
- 最后一名对局玩家离开，房间被删除；
- 终局后禁止继续落子，防止重复结算。

## 8. 服务端如何防止非法操作

每次落子都按顺序检查：

1. 房间是否处于 `PLAYING`；
2. 操作者是否为对局玩家；
3. 是否轮到该玩家；
4. 行列是否为合法整数且未越界；
5. 目标格是否为空；
6. 落子后是否胜利或平局。

不合法时只返回错误，不修改棋盘。典型错误码包括：

- `ROOM_NOT_FOUND`：房间不存在；
- `NOT_YOUR_TURN`：未轮到该玩家；
- `CELL_OCCUPIED`：格子已被占用；
- `SPECTATOR_READ_ONLY`：观战者不能落子；
- `INVALID_MOVE`：坐标不合法。

## 9. 胜负和积分

规则支持两种模式：

- 3×3 棋盘，三子连线获胜；
- 5×5 棋盘，四子连线获胜。

服务端从横、竖、主对角线、反对角线四个方向扫描连续棋子。棋盘填满且无人获胜时判为平局。

积分规则：胜利 `+30`、平局 `+10`、失败 `+2`。排行榜先按积分排序，再按胜场排序。

写排行榜时先写临时文件，再替换正式文件；并发结算会排队写入，降低文件互相覆盖的风险。

## 10. HTTP 接口

| 方法和路径 | 作用 |
|---|---|
| `GET /health` | 检查服务是否运行，并返回房间数 |
| `GET /games/daily` | 获取每日残局 |
| `GET /rankings?limit=20` | 获取排行榜 |
| `POST /rankings` | 提交比赛结果（演示接口） |
| `WS /ws` | 建立实时对局连接 |

HTTP 适合普通数据查询，WebSocket 适合需要实时同步的对局。

## 11. 自动化测试

当前 Server 测试覆盖 16 个场景，主要包括：

- 公共规则和 WebSocket 协议契约；
- 真实 WebSocket 连接和完整胜局；
- `WAITING → PLAYING → FINISHED` 状态迁移；
- 正常胜利、平局、认输和单次结算；
- 越界、重复格、错误回合、观战者落子；
- 玩家或观战者离开、房间重置和删除；
- 每日残局格式与答案。

运行测试：

```bash
cd server
npm test
```

测试的意义不是证明“绝对没有 Bug”，而是保证关键规则在修改代码后不会被意外破坏。

## 12. 启动与演示

```bash
cd server
npm install
npm start
```

默认端口为 `9527`。答辩演示顺序建议：

1. 访问 `/health`，证明服务端在线；
2. Android 创建房间；
3. 鸿蒙输入房间码加入；
4. 两端交替落子，展示棋盘同步；
5. 故意连续落子，展示服务端拒绝错误回合；
6. 完成胜局，展示终局锁定和排行榜变化；
7. 运行 `npm test`，展示自动化测试全部通过。

## 13. 当前边界与后续优化

这是课程演示版本，已保证核心对局一致性，但不是生产级系统：

- 房间只在内存中，服务重启后会丢失；
- 玩家 ID 由客户端提供，没有登录鉴权；
- 排行榜使用 JSON 文件，不适合大量并发；
- `POST /rankings` 是演示接口，生产环境应只允许权威对局内部结算；
- 当前使用 `ws://`，公网正式环境应使用 `wss://`；
- 暂未实现断线重连、心跳检测和多服务器部署。

后续可升级为：数据库 + 登录令牌 + Redis 房间状态 + 断线重连 + HTTPS/WSS。

## 14. 答辩常见问题

**为什么不用客户端直接同步？**  
客户端不可信且可能状态不一致，所以由服务端统一验证和广播。

**为什么选择 WebSocket？**  
对局需要服务端主动、低延迟地推送状态，长连接比轮询更合适。

**如何保证两端棋盘一致？**  
两端不互相修改对方状态，都接收服务端广播的完整权威快照。

**如何防止重复结算？**  
房间进入 `FINISHED` 后不再允许落子或认输，结算只在状态首次结束时执行。

**服务端最核心的模块是什么？**  
`room-service.js`，它实现房间状态机和所有对局合法性检查。

**服务端宕机后怎样恢复？**  
当前房间无法恢复，这是内存存储的边界；生产版本应把状态保存到 Redis 或数据库。
